# Airレジ公式API連携の実装準備

調査日: 2026-10-14。状態: AIOb側の同期基盤を実装・架空データで検証済み。公式API仕様・利用条件の確認待ち。Airレジへの実接続は未実装・未接続。

## 目的

既存のAirレジを使い続けながら、売上を自動でAIObへ取り込み、店舗の最新状況を確認・解析する。CSVは過去データ補完などの補助として扱う。

## 公式情報で確認できたこと

- Airレジの店舗別「データ連携API」画面で利用を有効化し、APIキー・APIトークンを発行する。複数店舗でも設定は店舗ごと。
- 対象は取引情報（会計、領収書印刷、伝票削除、会計修正、返品・返金、返品取消）、入出金情報、精算情報。
- 過去データの連携は開始時点から過去2か月前まで。精算情報は実際に精算したデータが対象。
- 公開FAQで確認できる接続方法には、実装に必要なAPIのURL・認証ヘッダー・リクエスト/レスポンス定義・ページング・更新間隔が掲載されていない。一般公開の開発者仕様書は今回の調査では見つからなかった。
- 連携システムの公式一覧にAIObは掲載されていない。未掲載サービスについては公式が連携希望の連絡を案内している。掲載の有無だけで、API利用不可または提携契約必須と断定しない。
- メニューの全件マスター取得・更新と勤怠取得は、公開されたAirレジAPIの対象一覧では確認できない。
- Airシフトの公式FAQでは、シフトボード・freee人事労務・Airワーク給与支払・Airメイトとの連携を案内している。AIObの勤怠連携は別に条件を確認する。

## 現在のAIObとの差分

- `types/phase4.ts` の `air_regi` はファイル取込のデータ元名。API接続を意味しない。
- `lib/phase4/sales-import-data.ts` のデータ元作成は `connection_type: file_upload`。店舗別Airレジ認証・API同期処理はない。
- 既存の取引・商品明細・売上集計・店舗AI文脈は表示先として利用できる。
- APIイベントの取消・返金・修正を、CSVの新規行追加処理へそのまま渡さない。元取引の履歴を保ち、現在有効な会計状態から集計する必要がある。
- メニュー表示は売れた商品の明細と、販売前を含む商品マスターの同期を分ける。前者の取得だけで全メニューの同期完了と表示しない。

## 実装・検証済みのAIOb側基盤

- 店舗オーナー／運営管理者のみが管理する接続設定。店舗と法人を照合し、キー・トークンは店舗に紐付く認証付き暗号でサーバー側に保存する仕組み。
- 同期の排他ロック、有効な所有者権限の再確認、失効時の停止、差分カーソル、再試行と待ち時間。取込・カーソル・集計を同一DBトランザクションで反映。
- 元取引IDと更新時刻による重複防止・古い更新の除外・同一更新の矛盾検知。修正・返金・取消は履歴を保持し、現在の状態を既存売上ページへ反映。
- 取消を売上と件数の集計から除外。取引明細では取消・返金を区別。精算や現金入出金は売上へ混ぜない。
- 停止／再開、接続の削除済み移動／復元。削除時はローカルの暗号化キーを消去し、取引履歴は保持。復元だけでは再開しない。Airレジ側のキー失効は別操作。
- PC1440px・スマホ390pxで設定画面と削除／復元を確認。スタッフ・店長・別法人・未所属・停止権限・DB直接操作の拒否を検証。
- 公式仕様が未確認の間は `getAirRegiAdapter()` が常に `null`。本番のモックや任意URL呼出しはなし。秘密情報入力・実接続・自動取込は有効化しない。
- Cron入口は既存の保護方法で追加したが、定期実行は登録していない。取得間隔・API反映遅延・全店舗での実行容量は正式仕様の確認後に設計・検証する。
- AI会話にも接続準備中・未確認範囲を共有し、取消を有効取引の件数から除外。商品明細の売上集計と、商品マスター更新・在庫減算・勤怠取得は別機能であり、後者は未実装。

`lib/airregi/contracts.ts` は**AIOb内部の正規化形式**。Airレジのレスポンスを推測した仕様ではない。公式アダプターで営業日・税額・割引・会計修正・返品・返品取消の意味と、全体で一意の店舗／取引IDを対応付ける。タイムアウト・レスポンスのサイズ制限・ページングも公式アダプターで実装する。

## 仕様書を受領してから必要な実装

1. 店舗設定からAPIキー・APIトークンを保護して保存。AIObの店舗とAirレジの店舗を照合し、別店舗・別法人の混入を防ぐ。
2. 正式仕様に沿う読み取り専用の接続確認と、許可された範囲の初回取得を実装。店舗名・期間・取得対象・実際の同期間隔を利用者へ表示。
3. 差分同期、ページング、再試行、レート制限、同期途中の再開を実装。正式にWebhookが提供されるなら検証・重複防止を備える。未確認のWebhookや取得間隔を仮定しない。
4. 取引識別子・更新情報を仕様から確認して、再取得で売上が重複しない反映処理を実装。会計修正・返品・取消・返品取消と、営業日変更を検証。
5. 確定した取引と商品明細から売上ページの数値・グラフを更新。精算・入出金と売上を二重計上しない。
6. AIは最新の集計・明細差分を参照。毎回すべての過去売上を読み直す設計を避け、取り込み時刻とデータの鮮度を維持。
7. 商品マスター・勤怠の仕様が利用可能なら別の取得処理を追加。未対応項目は接続できたように表示しない。
8. 連携解除、再接続、秘密情報の失効・削除、履歴保持を実装。停止・閲覧者・別店舗・別法人のアクセス拒否と、同期障害後の復旧を検証。
9. 正式仕様による接続を隔離環境で検証後、店舗オーナー自身に接続先を確認してもらい実データで検証。現在の開発環境にオーナーが同席・ログインする前提にしない。

## 先に必要なもの

- リクルート提供のAPI仕様書・検証方法。キーだけでは呼び出し先やレスポンスの意味を実装できない。
- 連携事業者の登録・申請の要否、AIObの店舗経営解析という用途が利用可能か。
- Webhookまたは最短取得間隔、レート制限、クラウド反映の遅延、履歴・修正取得条件。確認前に「完全リアルタイム」を保証しない。
- yoomiが勤怠に利用しているAirシリーズの正確なサービス名。

店舗側のAirIDログインは、汎用連携の開発・検証後の接続段階で行う。yoomiの勤怠サービス名は未確認のままであり、売上連携の基盤開発を妨げない。

問い合わせ文案は同じフォルダーの `airregi-api-inquiry.txt`。送信のユーザー承認あり。公式フォームへ入力済み。返信先の到着確認とフォームのプライバシーポリシー同意は未完了のため、**まだ送信していない**。個人情報はこの公開リポジトリへ記録しない。

検証: `npm run test:airregi`、型検査・ビルド、`AIRREGI_STAGING_CLI_DIR=<ステージング専用CLI設定> npm run test:staging:airregi`。ステージング実地試験は一時的な架空店舗のみで実行し、試験後に片付ける。実店舗データ・メール・外部Airレジ・AI APIにはアクセスしない。
