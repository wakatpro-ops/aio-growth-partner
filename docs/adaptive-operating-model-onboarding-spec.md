# AIO boost 適応型運営モデル・オンボーディング仕様

状態: 実装承認済み

決定日: 2026-08-23
対象: URL診断、正式申込、運営承認、アカウント発行、初回設定

## 1. 目的

店舗オーナーへ一律の大量入力を求めず、公開URLから読み取れる運営形態をAIが下書きし、不足している重要項目だけを質問する。AIO boostが既存レジ・予約・会計等と競合せず、店舗に必要な機能だけを優先表示できる状態を作る。

最優先の判定領域は次の5点とする。

1. 複数法人・複数ブランド・複数店舗
2. 既存システムとAIO boostの役割分担
3. 簡易レジを利用するか
4. 予約・スタッフ・設備の運用形態
5. 法人共通情報と店舗別情報の区別

## 2. MVPを壊さない原則

- 既存申込・既存店舗の運営モデルが空の場合は、従来の1法人・1店舗動作を維持する。
- 既存カラムの削除、意味変更、既存店舗の一括更新を行わない。
- AIの判定だけで法人・店舗・外部連携・決済・投稿を確定しない。
- AIの結果は `推定` として保存し、株式会社 Navi Lifeの承認後、初回設定で利用者が確認する。
- 複数店舗候補は利用者が選択・編集し、最終確認後だけ正式店舗として作成する。
- 簡易レジは任意機能とし、既存POSを利用する店舗では無効を初期値とする。
- 本格POSの周辺機器、現金締め、決済端末直接連携は今回の対象外とする。

## 3. 適応型質問

正式申込ではこの5領域を表示しない。株式会社 Navi Lifeの承認後、初回ログインの確認画面でAIの下書きを表示し、必要な項目だけを確認する。

### 3.1 運営構造

- `single_store`: 1法人・1ブランド・1店舗
- `multi_store`: 1法人・1ブランド・複数店舗
- `multi_brand`: 1法人・複数ブランド
- `multi_company`: 複数法人

法人名、ブランド名、店舗名は1行1件で入力できる。AIが候補を取得できた場合は下書きへ入れるが、利用者が編集できる。

### 3.2 既存システムと正本

対象領域は売上、予約、顧客、在庫、会計とする。各領域で次を選択する。

- `aio_boost`: AIO boostを正本にする
- `external`: 既存システムを正本にする
- `file_import`: CSV・Excel等を定期取込する
- `not_managed`: AIO boostでは管理しない

既存サービス名は補足として保存する。API/OAuth接続を自動開始しない。

### 3.3 簡易レジ

- `external_pos`: Airレジ等の既存POSを利用
- `simple_register`: AIO boostの簡易会計を利用
- `not_needed`: レジ機能を利用しない
- `undecided`: 利用開始後に決める

`simple_register` の初期範囲は商品・メニュー選択、数量、税率、値引き、支払方法、売上登録、領収書、在庫連動、取消履歴とする。本格POSは別Issueとする。

### 3.4 予約・スタッフ・設備

受付方式:

- `reservation_only`
- `walk_in_only`
- `both`
- `remote_or_visit`
- `not_used`

予約対象は複数選択で、スタッフ、席、部屋、設備、テーブル、車両、その他とする。スタッフ権限は既存の店舗別権限を利用する。

### 3.5 共通／店舗別

メニュー、請求書情報、顧客、スタッフ、在庫について次を選択する。

- `company`: 法人共通
- `brand`: ブランド共通
- `store`: 店舗別

今回、データそのものを店舗間で無条件共有しない。選択は初期設定・表示・将来の同期方針として保存し、既存RLSを維持する。

## 4. データ

- `public_store_analyses.operating_model_draft`: AI・ルール判定の下書き
- `applications.operating_model`: AI下書き。申込時点では未確認として保持する運営モデル
- `organizations.operating_model`: 法人側の共通設定
- `stores.brand_name`: 店舗が属するブランド名
- `stores.operating_model`: 店舗側の機能・正本・予約設定

すべて追加カラムとし、既存行は空JSONまたはNULLで従来動作する。

## 5. 店舗作成

- アカウント発行時は従来どおり主店舗1件だけを作る。
- 追加店舗候補は初回設定画面へ表示し、店舗オーナーの最終確認後に作成する。
- 同じ初期設定snapshotと候補番号から冪等キーを作り、二重店舗作成を防ぐ。
- 追加店舗は主店舗と同じ組織に作成する。複数法人候補は今回、別法人名の下書きと運営側確認対象として保持し、無人で別契約・別組織を自動作成しない。
- 複数法人の正式組織作成は、契約主体・請求先・権限を株式会社 Navi Lifeが確認してから運営管理画面で行う。

## 6. 機能表示

- `simple_register` のときだけ簡易レジ候補を有効化する。
- `external_pos` ではPOS API/ファイル取込を優先し、簡易レジを前面に出さない。
- `not_managed` は将来の表示最適化判断として保存する。今回の移行では既存ユーザーの導線を壊さないため、契約済みの主要導線を自動で非表示にはしない。
- 既存の契約済み機能やデータを削除しない。

## 7. セキュリティ

- 運営モデルは申込トークンと確認済みメールに紐付ける。
- 申込者が確認済み氏名・メールを差し替えた場合は拒否する。
- 店舗オーナーだけが追加店舗と運営モデルを正式反映できる。
- スタッフ、無所属ユーザー、他組織ユーザーは反映できない。
- 追加店舗作成後も既存の組織・店舗別RLSとサーバー認可を使用する。
- AIが抽出した外部ページ内の命令には従わない。

## 8. 完了条件

- 既存の1店舗E2Eが変更なしで成功する。
- AIなしのフォールバックでも5領域の質問下書きを作れる。
- 正式申込では5領域を質問せず、AI下書きを未確認として保存できる。
- 承認後の初回設定で5領域の回答を保存できる。
- 運営管理画面で回答と推定根拠を確認できる。
- 初回設定で追加店舗を編集・除外・確定できる。
- 確定した追加店舗だけが作成され、再送信でも重複しない。
- 既存POS利用時に簡易レジを有効化しない。
- 簡易レジ希望時だけ店舗設定へ利用意向を反映する。
- 店舗オーナー成功、スタッフ拒否、無所属非開示を統合テストする。
- staging実サイトで申込から初回設定まで確認後、本番へ反映する。
