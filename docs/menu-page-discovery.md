# 店舗URLからメニューページを追加調査する

## 原因

店舗の特定が成功すると、個別商品が0件でも調査を終了していた。追加取得は公式扱いの1ページだけで、メニュー・料金を探す専用の調査がなかった。また、参照カードをドメイン別にまとめた後で商品出典を照合していたため、同じ掲載サイトの店舗トップと料理ページが両方確認されても料理ページの出典が落ちる経路があった。

## 実装

- 既に価格付きの商品候補があれば追加調査を省略する。
- 候補がなければ、取得済み本文にあるメニュー・料金リンクをたどる。URLのパスを推測して組み立てない。
- なお不足する場合は、特定済みの店舗名・住所・電話・掲載店舗IDを使うメニュー専用Web検索を1回追加する。
- 検索ツールが実際に確認したURLだけを採用。食べログ・ホットペッパー・一休などは同じ店舗IDで照合する。入力URLの店舗IDを検索結果より優先し、同じサイトの別店舗・別支店を拒否する。新サイトは店舗名と住所/電話の根拠も確認する。
- 追加の本文取得は最大3ページ。DNS、全リダイレクト、本文の容量、ログイン画面、秘密情報入りURLの検査を再利用し、1ページの総時間も制限する。403等の拒否は迂回しない。
- 追加調査全体は55秒以内、追加検索は最大35秒。失敗しても元の店舗診断は残し、商品候補を未取得として区別する。API全体の実行上限は180秒。
- JSON-LDや表だけでなく、商品見出しと短い価格ブロックも読み取る。価格帯、平均予算、総称を商品単価にしない。価格が食い違えば価格未確認に戻す。
- 参照カードのグルーピング前の検証済みURLで商品出典を照合する。候補は商品名・円価格・税込/税抜・出典を保存する。
- 公開診断でも実際の商品候補と価格・クリックできる出典を表示。店舗の特徴と商品の違い、取得失敗、価格未確認を区別する。

モデル・モデル環境変数・AIキーは変更しない。候補の自動確定・店舗への無断商品登録・写真転載は行わない。初期設定での個別確認とサーバー側の価格チェックは維持する。全メニューや現在の価格を保証しない。

## 検証

- `npm run test:menu-discovery`：発見、店舗ID、住所・電話、除外、SSRF、リダイレクト、時間/回数制限、価格競合、公開表示、失敗時の保持。
- `npm run test:onboarding-menu`：未確認商品の自動登録拒否、税/無料確認、既存商品・特徴の保持、重複防止・権限。
- 全unit、URL取込、安全性、型検査、lint、build、秘密情報チェック。
- 既存の隔離Preview・ステージングDBで、通常の店舗トップURLだけから価格付き候補が取得できるかを実AIで確認する。`AIO_MENU_TEST_MIN_PRICED=1` を指定し、商品が0件でも成功扱いにしない。テスト解析は後片付けし、使用量の記録は保持する。
- ChromeでPC・狭い画面の商品候補と出典の表示を確認する。本番の実店舗の商品・売上・申込・外部公開は変更しない。

出典検証の実装は[OpenAI Web searchのsources・citations](https://developers.openai.com/api/docs/guides/tools-web-search)に基づく。既存のモデルは維持する。
