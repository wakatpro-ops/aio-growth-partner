# Square読み取り専用連携

## 範囲と状態

実装対象は公式OAuth、店舗選択・確認、完了注文と返品・返金・取消の売上集計。Squareの決済・返金実行、商品マスター・在庫数・勤怠の同期は対象外。Airレジの未公開APIアダプターは引き続き無効のまま。

この変更は初期状態で無効。アプリ作成・単体テスト・ビルド成功だけで、実店舗接続や本番利用の検証が完了したとは扱わない。

## 公式仕様

- [OAuth](https://developer.squareup.com/docs/oauth-api/overview)：店舗オーナーがSquareへ直接許可。加盟店の個人アクセストークンを要求しない。
- [SearchOrders](https://developer.squareup.com/reference/square/orders-api/search-orders)：APIバージョン `2026-09-16`、更新日時順、固定期間・同一条件のカーソルで取得する。
- [返品・交換](https://developer.squareup.com/docs/orders-api/order-returns-exchanges)：返品・カスタム返金は別の返品注文として取得し、`net_amounts`の符号付き純額を利用。`refunds`と二重に減算しない。

要求スコープは `MERCHANT_PROFILE_READ` と `ORDERS_READ` のみ。顧客氏名・カード明細・注文メモ等は取得応答から保存対象へ転記しない。

## 環境と接続手順

既存Vercel・Supabase契約を再利用。環境変数は `.env.example` に名称のみ記載。秘密値はVercelのSecretへ保存し、Git・チャット・平文ファイルへ置かない。

Sandboxはステージング専用、明示した架空店舗UUIDの許可リストを必須とする。Productionは別のアプリ情報と戻り先で設定し、承認・実接続試験の後に公開範囲を広げる。SandboxアプリIDは `sandbox-sq0idb-`、Productionは `sq0idp-` で始まる。

1. `202610240001_square_pos.sql` を適用する。
2. 公式コンソールに、その環境の `/api/square/oauth/callback` を登録する。
3. Squareアプリ秘密キーと専用のトークン暗号化キーを保護済み環境変数へ保存する。
4. 環境・アプリID・戻り先・許可する架空店舗を指定し、テスト時だけ `SQUARE_LOGIN_ENABLED=true` にする。
5. 店舗オーナーが「設定→外部連携→Square」から許可し、AIOb店舗とSquare店舗を選択・確認する。接続直後には自動で店舗を決めない。
6. テスト売上の取り込み・再試行・訂正・停止・再接続を実際のSandboxで確認してから、本番の設定へ進む。

SandboxのOAuth試験は、デフォルトの全権限テストアカウントを流用せず、自動権限付与を無効にした日本のテスト加盟店を作り、そのSandbox Dashboardを開いてから行う。Sandboxは `session=true`、Productionは明示的に再認証する `session=false` とする（[公式の環境別制約](https://developer.squareup.com/docs/oauth-api/walkthrough)）。

## 安全性とライフサイクル

- オーナー／有効な運営管理者だけが接続操作可能。DBでも所属・有効状態を再確認する。スタッフ・店長・別法人は不可。
- ランダムstateはHttpOnly Cookieとハッシュ保存した一回限りのDBセッションで照合。利用者・店舗・法人・環境・戻り先を固定する。
- OAuth後は短時間の暗号化された確認待ち情報だけを保存。明示確認前に売上同期しない。設定版が変わった古い画面では接続を上書きできない。
- 環境・merchant・locationを組み合わせた外部識別子は一意。同じSquare店舗を別のAIOb店舗に紐付けない。接続済みの店舗識別子は黙って切り替えない。
- AES-256-GCMの追加認証データに法人・店舗を含める。期限前にトークンを更新し、同期リースと旧暗号文の比較で競合を防ぐ。
- 停止・再開・削除済み・元に戻すを備える。削除はローカル資格情報と確認待ちトークンを消去し、既存売上・変更履歴・監査を残す。復元後は再接続が必要。
- アプリ全体のSquare許可取り消しは、他店舗にも影響し得るため、店舗単位の削除では実行しない。

## 同期と集計上の注意

初回は更新日時が直近90日の注文から取得。以後は重複期間を設け、1ページ100件をリース付きで処理する。ページ・カーソル・集計更新は同一DBトランザクション。注文ID＋更新日時で冪等化し、古い版は無視、同じ版で内容が違う場合はページ全体を保留する。

Cronは毎分起動し、最大2接続・各1ページを処理する。大量の初期データ、Square側の索引反映、オフラインPOS、障害・制限時は遅れる。Webhookはこの段階では未実装であり、完全リアルタイムや一定秒数での反映を約束しない。

日付はSquare注文の完了日時を日本時間で日付化する。店舗独自の締め時間による営業日集計とは異なる場合がある。日本円・日本時間の有効な店舗だけを選択する。

返品・交換の金額は純額で集計するが、複雑な交換やカスタム返金を架空の商品へ割り振らないため、その商品の内訳は未分類になる。複数支払方法の注文は「複数の支払方法」とし、金額を推測で分割しない。注文金額と商品明細との差は調整額として保持する。

商品未配分のSquare取引は相殺後の差額が0でも件数で検知し、商品グラフを確定した売れ筋ランキングと区別する。AI月次分析は取引ごとに金額を突合し、未配分がある月のランキングを保留する。いずれかの月が不完全なら商品別の前月比較も行わない。合計売上を商品明細の合計に置き換えない。

返金元の支払方法を取得できない返品注文は未設定として区別する。支払方法別に負額の区分がある場合は、不適切な割合になるドーナツグラフを表示せず、符号付き金額の表へ案内する。

CSV等で同じ売上を既に取り込み済みの実店舗は、切替期間・重複範囲の照合が必要。初回接続には未取り込みの確認を必須とし、直近90日のSquare由来CSVを検出した場合は接続を保留する。一般CSVの中身まですべて自動同定できるわけではないため、その場合も運営確認後の切替が必要。API内の重複防止は、別のCSVから入った同一売上の同定まで保証するものではない。
