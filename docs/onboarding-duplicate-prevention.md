# 初期設定の追加店舗・重複防止（2026-10-13）

## 原因

公開情報から抽出した追加店舗候補が初期状態で選択済みだった。候補の自店判定は保存前の店舗名・住所との単純一致だけで、利用者が修正した名称・URLとの再比較がなかった。さらに同じ候補の再実行で、削除済み店舗を upsert により復元する可能性があった。

## 修正

- 追加候補は未選択。途中保存の再開時も選択を引き継がず、最終確認で別支店だけ明示的に選ぶ。
- 追加店舗の選択欄を折り畳みから出し、住所・URLも確認・訂正できるようにする。
- 単独店舗として確定した場合は、送信値に追加選択があっても追加しない。
- 表記揺れ・URL追跡パラメータを正規化し、修正後の主店舗と候補同士を再比較。同名ブランドでも住所が異なる支店を一律には除外しない。
- 保存前に同じ法人の登録済み・削除済み店舗とも比較。登録済みの競合は追加対象から外すよう案内し、削除済みは削除済み一覧から明示的に復元する。
- 同じ候補キーの部分失敗リトライは既存店舗を再利用し、プロフィール・請求番号・初期設定履歴を上書きしない。
- 既存店舗データの削除・統合・復元はこの修正では行わない。

## 検証

- `npm run test:initial-setup`: 11件の単体テストと実サーバーワークフローのインメモリテスト。
- `node --experimental-strip-types scripts/test-initial-setup-duplicates.mjs --staging`: 既存ステージングに限定した架空データで、主店舗の訂正、既存店舗・削除済みの保護、部分失敗リトライ、完了後の再実行、同一スナップショットの同時送信、法人分離、オーナー権限ゲートを確認。作成した架空データは終了時に削除。
- 上記ワークフローテストは認証コンテキストをスタブ化している。ログイン・RLSのエンドツーエンド試験ではない。
- `npm run test:initial-setup:layout`: 実フォームのSSRと実CSS、架空の入力で320/390/1280pxを検証。選択欄の可視性・未選択・横溢れなしを確認し、画像を一時ディレクトリへ保存。認証済み本番ページでは操作しない。
- 初期設定の静的チェック、クライアント秘密情報チェック、変更箇所lint、TypeScript、本番ビルドを実行。

## 範囲

今回の防止対象は初期設定からの追加店舗作成。別スナップショットから異なる候補キーで同時登録するケースや、手動店舗作成・申込承認全体をDB一意制約で一律禁止するものではない。名称だけの一意制約は、同名の実在支店を誤って拒否するため導入しない。
