# AIO boost 予約ハブ・外部予約一元管理 仕様

## 目的

AIO boostを予約管理の正本として使える店舗には、予約・顧客・担当者・設備・空き枠を一つの画面で管理できる基盤を提供する。既存の予約媒体を使う店舗には、媒体を急に置き換えず、読み取り専用の並行運用から段階的に一元化する。

「予約サイトを新しく作る」ことだけを目的にせず、電話・店頭・LINE・外部予約媒体を含む予約業務の確認先をAIO boostへ集約する。

## 守る原則

- 公式APIがある接続先は公式APIを優先する。
- 公式APIがない接続先だけ、利用規約と契約上の許諾を確認した専用コネクタとして画面連携を検討する。
- CAPTCHA、二段階認証、本人確認を回避しない。必要な時は店舗担当者へ操作を依頼する。
- 外部接続用の認証情報は暗号化し、運営管理者を含め平文表示できない構造にする。
- 接続先ごとに処理を分離し、1媒体の仕様変更で予約ハブ全体を停止させない。
- 外部連携は、読み取り専用の並行運用、差分確認、限定的な書き込み、本格同期の順に開放する。
- 同期失敗、重複、競合、認証切れを画面で説明し、監査履歴を残す。
- 予約の作成・編集・削除・復元・重複防止・認証認可が完成するまで、利用可能な予約機能として案内しない。

## 段階導入

### 第1段階: AIO boost独自予約基盤

対象:

- 予約台帳（日付、開始・終了、顧客、サービス、担当者、設備、受付経路、状態、メモ）
- サービスごとの所要時間・準備時間・価格・予約受付可否
- 担当者・席・部屋・設備など予約資源の管理
- 店舗内の時間重複検出
- 予約の作成、編集、完了、キャンセル、無断キャンセル、削除、復元
- 顧客台帳との任意の関連付け
- 操作履歴
- 店舗単位の認証・認可
- PCとスマートフォン双方で使える一覧・入力UI

第1段階では、外部媒体への自動書き込みはしない。

### 第2段階: LINE予約窓口

- LINE Messaging APIのWebhook受信
- 予約希望の聞き取りと空き枠候補提示
- 予約確定前の店舗確認または明示的な自動確定設定
- リマインド、変更、キャンセルの案内
- 顧客同意と配信停止の管理

### 既存LINE予約からの移行

既存のLINE公式アカウントや予約サービスを利用している店舗は、現在の受付を止めずに次の順番で移行する。

1. 現在の予約サービス、LINE公式アカウント、管理権限、未消化予約数、データ出力方法を店舗単位で記録する。
2. 優先して移す「これから来店する予約」と、必要な顧客・メニュー・担当者の範囲を確認する。
3. 旧サービスのWebhookと受付を維持したまま、AIO boost側でテスト予約を確認する。
4. 店舗責任者が切替日時と問題時の復旧方法を承認する。
5. 運営管理者が対象店舗の接続先、Webhook、予約台帳への反映を確認して移行完了にする。

移行計画にはパスワード、アクセストークン、Webhook署名秘密、二段階認証コードを保存しない。店舗担当者の保存操作だけで既存Webhookやトークンを変更しない。完了後も旧サービスの履歴とAIO boostの監査履歴を保持し、障害時は運営管理者が復旧確認を記録できるようにする。

予約データはCSV・TSV・Excel（XLSX・XLS・XLSM）を一括解析し、列名から予約日時、顧客、連絡先、メニュー、担当者を判定する。マクロは実行せず、保存済みセル値だけを扱う。元ファイルは保存せず、店舗別RLSで保護した正規化プレビューだけを保持する。過去予約と判定不能行は理由付きで除外し、店舗が一覧を確認した将来予約だけを `pending`（店舗確認待ち）で予約台帳へ取り込む。行ごとの質問や自動確定は行わない。

移行計画は店舗・法人の複合外部キー、RLS、Server Action認可で分離する。認証済みでも無所属の利用者、別法人・別店舗の利用者、閲覧者は移行計画を閲覧・変更できない。

#### 実装する安全境界

- 店舗管理者が発行する1回・15分有効の店舗連携コードで、LINE利用者を一つの店舗へ関連付ける。コード本体は保存せずHMACだけを保持する。
- LINE利用者IDはサーバー上で暗号化し、照合にはHMACを使う。画面・監査ログ・Webhook履歴へ平文を出さない。
- Webhookは生の本文に対する署名を検証してからJSONを解析し、イベントIDを一意に保存して重複実行を防ぐ。
- 同意前は店舗関連付け以外の予約処理を行わず、配信停止は会話途中でも即時に受け付ける。
- 自動確定の初期値はオフ。店舗が明示的にオンにしても、担当・設備が未指定で競合をDBロックできない予約は店舗確認待ちにする。
- 予約作成・変更は第1段階の競合検査を再利用する。キャンセル、リマインド、失敗・再試行も監査履歴へ残す。
- 店舗連携を削除しても予約・同意・監査履歴は保持し、未送信リマインドだけを停止する。

### 第3段階: 外部予約媒体の読み取り専用コネクタ

- 接続先ごとの契約・技術調査
- 予約取得、差分表示、重複候補の提示
- 同期時刻、成功・警告・失敗、再認証要否の表示
- 店舗が確認するまでは外部媒体へ書き戻さない
- 同一人物・同一時間帯・同一媒体予約の重複候補を統合前に確認

「APIあり」は、一般公開API、契約後に開示されるAPI、予約システム間だけの提携連携を区別する。外部サイトの画面を取得できるという理由だけで接続済みとは扱わない。

店舗画面では8媒体の調査結果、契約プラン、媒体側店舗ID、申請状況を店舗単位で管理する。パスワード、APIキー、二段階認証コードはこの準備画面へ入力させない。提供会社の許諾、暗号化した認証情報、対象店舗との一致、読み取りテストを運営会社が確認するまで `接続済み` を表示しない。

### メール転送による補完: 店舗AI受信箱

小型店舗では予約、問い合わせ、クレーム、請求、仕入の連絡先が一つのメールアドレスへ集まることが多い。そのため予約メールだけを店舗側で選別させず、1店舗につき一つの `store-<推測困難なコード>@in.aioboost.jp` を発行する。店舗は普段のメールをこのアドレスへ転送し、AIO boost側で次の順に処理する。

1. Webhook認証、宛先店舗、店舗状態、重複を確認する。
2. パスワード再設定、認証コード、カード情報、本人確認書類、秘密鍵などを先に除外する。件名・本文・添付は保存しない。
3. 予約、問い合わせ、クレーム、口コミ、請求・領収、仕入・発注、在庫・配送、サービス通知、広告、未分類へ整理する。
4. 生本文と添付は保存せず、短い要約、分類理由、確信度、業務に必要な構造化項目だけを店舗別に保存する。
5. 店舗担当者が確認して、予約は既存の予約台帳へ反映する。他の分類は対応済み・処理しないを記録する。

初期値は必ず人による確認とする。予約メールは、店舗オーナー・店舗管理者・運営管理者が初回内容を確認し、「今後、この送信元・この形式・この予約種別は自動処理する」を明示的に承認した時だけ、店舗単位の学習済み形式として登録する。学習済み形式は、送信元、媒体、構造化した件名・項目ラベル、予約種別（新規・変更・キャンセル）から作るフィンガープリントで照合し、顧客名や予約日時などの個人値はフィンガープリントへ含めない。

2回目以降も、同じ店舗、送信元、媒体、予約種別、形式が完全一致し、予約番号と予約種別ごとの必須項目が揃い、解析確信度が基準以上の場合だけ自動反映する。新規予約は氏名・開始・終了、変更は対象予約番号・氏名・開始・終了、キャンセルは対象予約番号を必須とする。形式変更、必須項目不足、重複、日時衝突、変更・キャンセル対象が見つからない場合は、自動処理せず理由付きで確認待ちへ戻す。AIの自由文判定、別店舗の学習、送信元だけの一致では自動反映しない。

学習済み形式は店舗単位で一覧、停止、再開、削除、復元でき、適用結果と操作を監査履歴へ残す。担当店舗の編集権限を持つスタッフは受信結果を手動反映できるが、新しい自動処理形式の登録・変更はできない。メールへの返信、決済、アカウント設定変更、外部サービスへの書き戻しは行わない。

受信箱の発行・停止・再発行・削除・復元は店舗オーナー、店舗管理者、運営管理者だけが行う。担当店舗の編集権限を持つスタッフは受信結果の確認と予約反映を行える。認証済みでも所属なし、他法人、他店舗、停止・削除済みアカウントはページ、Server Action、API、DBの全境界で拒否する。

実メール受信の開始には、`in.aioboost.jp` 専用MX、SendGrid Inbound Parse、専用APIキー、Webhook認証を別途確認する。過去に露出した可能性があるキーは再利用せず、契約・課金状態を確認してから有効化する。

### 第4段階: 双方向同期

- 接続先ごとの許諾と十分な安定性が確認できた媒体だけ書き込みを開放
- 冪等キー、競合解決、再試行、障害隔離、監査ログ
- 読み取り専用へ即時に戻せる停止スイッチ

## 第1段階のデータ

### 予約サービス

- 店舗、名称、説明、所要時間、前後の準備時間、価格、色、予約受付可否、表示順
- 既存の商品・メニューとは任意で関連付ける。商品・在庫データを予約の都合で書き換えない。

### 予約資源

- 店舗、名称、種別（スタッフ、席、部屋、設備、テーブル、車両、その他）、同時受付数、色、表示順
- 店舗スタッフのログイン権限と予約担当者は別概念とし、必要な場合だけ関連付ける。

### 予約

- 店舗、顧客、予約サービス、予約資源、開始・終了、状態、受付経路、氏名・電話・メールの予約時点スナップショット、メモ
- 状態は `pending`、`confirmed`、`completed`、`cancelled`、`no_show`
- 受付経路は `aio_boost`、`manual`、`phone`、`line`、`external`
- 削除は論理削除とし、削除済み一覧から復元できる。

## 重複防止

- `cancelled` と削除済みを除く予約を対象に、同一予約資源の時間帯重複を拒否する。
- `start_at < existing_end_at` かつ `end_at > existing_start_at` を重複とする。終了時刻と次の開始時刻が同じ予約は許可する。
- 編集時は自分自身を比較対象から除外する。
- 画面の事前確認だけに依存せず、DB関数内でもロックして再確認する。
- 同一予約資源を割り当てない予約は、店舗の受付上限を設ける段階まで並行登録を許可する。

## 権限

- 運営管理者: 全店舗で閲覧・編集可能
- 法人オーナー: 所属法人の全店舗で閲覧・編集可能
- 店舗管理者・スタッフ: 割り当てられた店舗だけ閲覧・編集可能
- 閲覧のみ: 割り当てられた店舗だけ閲覧可能
- 認証済みでも組織・店舗のどちらにも所属しないユーザー: 一切閲覧・編集不可
- 別店舗だけに所属するスタッフ: 対象店舗を一切閲覧・編集不可

制御点はページ、Server Action、API、DB RLS/RPCの四層とする。存在の推測を防ぐため、対象外店舗は原則404相当として扱う。

## 画面

- 顧客ハブに「予約」への入口を追加するのは、第1段階のライフサイクルと権限テストが通った後とする。
- 予約一覧では「今日」「今後」「過去」「削除済み」を分ける。
- 一覧は時刻、顧客名、内容、担当・設備、状態を短く表示し、状態を色だけに依存しない。
- 作成・編集では、基本情報、日時、担当・設備、連絡先、メモの順に表示する。
- 保存直後に二重送信を防ぎ、完了後は予約詳細へ遷移する。
- 予約資源とサービスの設定は、予約画面から迷わず到達できる。

## 監査

次の操作で `audit_logs` を必ず記録する。

- 予約作成・編集・状態変更・削除・復元
- 予約サービス作成・編集・削除・復元
- 予約資源作成・編集・削除・復元
- 将来の外部接続、再認証、同期、競合解決、書き戻し

## 第1段階の完了条件

- 予約、サービス、資源の作成・閲覧・編集・削除・復元ができる。
- 同一資源の重複予約が、同時操作でもDB側で拒否される。
- 閲覧のみ・別店舗・未所属・停止済み・削除済みアカウントの負のテストが通る。
- 予約のない店舗でも空状態が理解できる。
- PCとモバイルで操作できる。
- lint、ユニットテスト、ビルド、認証認可統合テストが通る。
- DB反映後に本番で運営管理者・店舗権限それぞれの表示を確認する。

## 今回まだ行わないこと

- 外部予約媒体のID・パスワード収集
- 外部媒体への自動書き込み
- CAPTCHAや二段階認証の自動化
- 許諾未確認のスクレイピング
- POS、決済、会計を予約確定と同時に自動操作すること
- 任意の既存予約サービスへの汎用自動ログインと、許諾未確認のデータ取得
